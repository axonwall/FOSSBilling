## Route model — how a URL becomes a PHP method call

Verified against `src/modules/Api/Controller/Client.php` (route registration
and the HTTP/auth front door) and `src/library/FOSSBilling/Api/Dispatcher.php`
(the actual dispatch), plus `src/di.php` (`api_identity` / `api_dispatcher`
services) and `src/library/FOSSBilling/Api/{Identity,Proxy,AbstractApi}.php`.

1. **One route pair for everything.** `Client::register()` registers only
   `POST /api/:role/:class/:method` and `GET /api/:role/:class/:method`, with
   `:role` constrained to `guest|client|admin` and `:class` / `:method` to
   `[a-zA-Z0-9_]+`. Any other `/api/...` path falls through to `show_error`
   (error 879, "Unknown API call"). GET takes parameters from the query
   string; POST takes them from the request payload (form or JSON body;
   malformed JSON is rejected with error 400). `CSRFToken` is stripped from
   the parameter array before dispatch.
2. **Class/method mapping.** The controller concatenates the two trailing
   segments into a single call string: `$call = $class . '_' . $method`.
   `Dispatcher::dispatchWithArguments()` requires an underscore in that call,
   splits on the **first** underscore — the head, lower-cased, is the module
   name; the remainder is the PHP method name — checks the module is
   installed/activated (`Extension` service, error 715 otherwise), and builds
   the target class as:

   ```
   \Box\Mod\<Ucfirst(module)>\Api\<Ucfirst(role)>
   e.g. /api/admin/support/ticket_get_list
        -> call "support_ticket_get_list"
        -> Box\Mod\Support\Api\Admin::ticket_get_list($data)
   ```

   So for every endpoint in this catalog:
   `route = /api/<role>/<module-directory-name, lower-cased>/<php-method-name>`
   and the Next.js port should treat **the module segment as the first
   underscore-delimited token of the Twig/proxy call name**, not as a free
   path segment. Twig usage confirms the same model:
   `{{ admin.support_ticket_get_list(...) }}`, `{{ guest.system_version }}`
   (via `FOSSBilling\Api\Proxy::__call` -> the same dispatcher).
3. **Invocation shape.** Almost every API method takes a single `$data`
   array (the whole parameter bag) — 397 methods declare `($data)`, 99
   `(array $data)`, 5 `($data = [])` and 1 `(array $data = [])`, and 75
   declare no parameters at all; the only exceptions are
   `Extension\Api\Guest::languages($deep = false)` (a scalar flag instead
   of the data bag — the dispatcher passes it the data array positionally,
   so it is effectively a truthiness flag over the whole bag) and the
   `Servicecustom` `__call($name, $arguments)` magic method below. The
   dispatcher normalises this: a
   required first parameter receives the data array, an optional one
   receives nothing when the bag is empty. There is **no per-field PHP
   signature** to port — the request contract for each endpoint is its
   `required_params` plus its docblock `@optional` fields in the catalog.
4. **Required-param validation runs before the method body.**
   `Dispatcher::validateRequiredParams()` reflects on the target method's
   `#[RequiredParams(['name' => 'message', ...])]` attribute
   (`FOSSBilling\Validation\Api\RequiredParams`) and rejects missing /
   empty-string / empty non-numeric values with `InformationException`.
   A legacy equivalent survives in a handful of methods: a `$required = [...]`
   array passed to `$validator->checkRequiredParamsForArray($required, $data)`
   (`FOSSBilling\Validate`, identical semantics). The catalog merges both
   and labels each entry's `source`.

## Auth model — how role is enforced

All enforcement lives in `Api\Controller\Client::_apiCall()`, in this order:

1. **Global gates (every role):** config IP allow-list (`api.allowed_ips`,
   error 1002) and an optional referrer check (`api.require_referrer_header`,
   error 1004) if enabled in config.
2. **Role allow-list:** role must be `guest`, `client` or `admin` (error 701).
3. **Guest role: no identity required.** Anyone may call guest endpoints.
   Exceptions carved out in `checkGuestAuthentication()`: the combined calls
   `client_login`, `client_create`, `staff_login`, `cart_add_item`,
   `cart_remove_item`, `cart_apply_promo`, `cart_remove_promo`, `cart_reset`
   and `cart_set_currency` additionally require the pre-login session CSRF
   nonce (`CSRFToken` param or `X-CSRF-TOKEN` header, `hash_equals` against
   the session token) and a same-origin context (`Origin` must match
   `SYSTEM_URL` when present; `Sec-Fetch-Site: cross-site` is rejected);
   the three login calls must be POST (error 405 otherwise). Guest errors
   from non-FOSSBilling exceptions are sanitised to a generic message.
4. **Client / admin roles: session OR API-token (HTTP Basic) auth.**
   - If a Basic-auth username is supplied it must literally equal the role
     (`client` or `admin`, error 203); the password is then treated as the
     account's **API token**: for `client`, a `Client` entity with matching
     `apiToken` and status ACTIVE (error 204); for `admin`, an `Admin`
     (staff) entity with matching `apiToken` and status ACTIVE, excluding
     the cron admin account (error 205). A successful token login is
     converted into session state (`client_id` / `admin` session array).
     Missing user/password produce errors 201 / 202 / 206.
   - Otherwise a logged-in **browser session** is required
     (`is_client_logged` / `is_admin_logged` DI flags; failure is error 201,
     surfaced as "Authentication Failed"), **plus CSRF validation**
     (`_checkCSRFToken()`, unless `api.CSRFPrevention` is disabled or CLI):
     token accepted from JSON body / form / query `CSRFToken` or the
     `X-CSRF-TOKEN` header, compared with `hash_equals` to the session
     token, and — when present — the CSRF cookie must also match it.
   - Three combined calls are **session-only even when a token is offered**:
     `profile_api_key_get`, `profile_api_key_reset`,
     `profile_generate_api_key` (`shouldPreferSessionAuth()` forces the
     session path whenever a session exists; a token cannot be used to read
     or rotate itself).
5. **Rate limiting** is applied pre-auth for non-guest roles and again for
   all roles: policies `api_login` (for `*_login` calls), `api_guest`,
   `api_authenticated_ip`, and `api_authenticated_account` (keyed by
   `client:<id>` / `admin:<id>` once a session exists).
6. **Identity -> role is type-derived, not claimed.** After auth, the
   controller asks DI for `api_identity($role)`, which wraps the *session's*
   `loggedin_client` / `loggedin_admin` entity (or a fresh
   `FOSSBilling\Identity\Guest`); `Identity::typeFromObject()` re-derives
   the role from the object class inside the dispatcher, so the URL role
   cannot be used to impersonate another identity type. Side effect in
   `api_identity`: a client whose email is not yet validated gets
   `EmailValidationRequiredException` (HTTP 403 via the controller) for all
   `/api/client/...` calls except those under `/api/client/client/` and
   `/api/client/profile/`.
7. **Per-module staff permissions (admin role only).** Before instantiating
   the API class, the dispatcher checks
   `Staff::hasPermission($identity, $mod)` (error 725) unless an update
   finalization is pending and the call is finalization-allowed. Many
   methods additionally call `$this->checkPermissions('<module>', '<key>')`
   in-body (445 call sites inside endpoint bodies — the catalog records
   them per endpoint in `permissions`; the one remaining occurrence in the
   API classes sits in a private helper,
   `System\Api\Admin::checkUpdateFinalizationPermissions()`, reached from
   the update-finalization endpoints).

## Special-cased endpoints / dispatcher behaviour

* **`Servicecustom` Admin `__call` (magic, open-ended).** The only
  `__call` in any API class: `Box\Mod\Servicecustom\Api\Admin::__call($name,
  $arguments)`. If dispatch targets a method that does not exist on that
  class, the dispatcher accepts it when the class has `__call` (error 740 is
  only thrown without one) and the call is forwarded to the custom-service
  plugin (`customCall`) with `order_id` required in the data. In the catalog
  this appears as one entry with `is_magic_method: true` and a
  `wildcard_route` of `/api/admin/servicecustom/<any-undeclared-method>` —
  it is a wildcard family of endpoints, not a single route. The Client role
  exposes the same plugin mechanism as a normal declared method,
  `servicecustom/call`, with `#[RequiredParams(['order_id', 'method'])]`.
* **Update-finalization lockdown.** When an update finalization is pending
  (`FOSSBilling\UpdateFinalization`), **all** admin API calls are rejected
  with HTTP 503 in the controller (and module permission checks are skipped
  in the dispatcher) except the combined calls
  `system_update_finalization_status`, `system_finalize_update`,
  `system_complete_update_finalization` and `profile_logout`.
* **Cron over HTTP.** `GET|POST /api/guest/cron/run` runs the whole cron
  suite as a *guest* call, gated inside the method body: the Cron module
  config must enable `guest_cron` and set a `cron_hash`, the caller must
  pass a matching `hash` parameter (`hash_equals`), and runs are throttled
  to at most one per minute. It is the one guest endpoint with its own
  shared-secret check.
* **Login endpoints are guest-role.** `client/login`, `client/create`
  (signup) and `staff/login` live in the Guest API classes
  (`Client\Api\Guest::login/create`, `Staff\Api\Guest::login`) — the
  session they create is what later `client`/`admin` calls rely on; see the
  extra CSRF/POST requirements in the auth model above.
* **Unknown / inactive targets.** A route whose module is not installed or
  activated fails with error 715 before the class is loaded; a missing
  class or method fails with 740; a call without an underscore fails 710.
* **Error surface.** Responses are uniformly rendered by
  `ApiResponseFactory` as JSON; `AuthenticationRequiredException` is mapped
  to error 201 "Authentication Failed".


## How the script works

- Globs exactly `src/modules/*/Api/{Admin,Client,Guest}.php` (66 files; the `Api` module itself — controller/service — and all `tests/` trees are excluded by construction).
- For each `public function` it records module (directory name), role (file name), FQCN (from the file's `namespace` + `class`), method name, line number, the raw PHP signature with per-parameter name / type / required / default / variadic / by-reference, the declared return type, the docblock summary + `@return` + every `@optional` field, any `checkPermissions('<module>', '<key>')` calls in the body, and the route + dispatcher call string derived from the mapping above.
- Signatures, attribute arrays and bodies are extracted with a string/comment-aware balanced-delimiter scanner (no PHP runtime, no regex-only brace counting), so defaults like `[]` and messages containing brackets cannot corrupt the parse.
- Required params are merged from both enforcement mechanisms (`#[RequiredParams]` attributes and in-body `$required` arrays fed to `checkRequiredParamsForArray`), each entry labelled with its `source`. In-body arrays are captured wherever they appear in the body — a few are inside conditional branches (e.g. one in `Invoice/Admin`), so treat in-body entries as 'required on at least one path'. Ad-hoc `isset()` / `empty()` guards that throw hand-written exceptions are *not* normalised into `required_params`; they remain visible only in the PHP source.
- Re-run any time with `python3 extract_api_catalog.py` (options: `--repo`, `--out-dir`). Output is deterministic: endpoints are sorted by file and line, JSON is pretty-printed.
