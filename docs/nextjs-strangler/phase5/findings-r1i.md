### The live happy path IS verified in this sandbox — for TS

The batch brief assumed the sandbox could not verify the live happy
path. That is true for **PHP** (its fetch dies at the TLS layer:
`TLS connect error: … wrong version number for
"https://open.er-api.com/v6/latest/USD"`, code 9999, nothing
flushed) but **false for TS**: Node's fetch reaches the live API.
parity24's `cur_eur_live` and `cur_bogus_provider` cases both
returned `true` with EUR updated to **0.89213** (USD still 1.0) from
the exchangerate open API. So the TS provider mapping, request
shape, and response parsing are live-verified; only PHP's side of
the comparison is sandbox-blocked. The two cases are recorded in
parity24 as an expected sandbox asymmetry (PHP 9999 error asserted,
TS success + plausible rate asserted), not as failures. One
normalization inside parity24: after the live case, EUR's
`updated_at` is reset to NULL, because TS's successful fetch stamps
it while PHP's failed fetch leaves it NULL — downstream manual-skip
and missing-key cases then compare the paths, not that residue.

## 3. D3 — binary/download endpoints: ALL PORTED

### Non-JSON route support (`route.ts`, `dispatch.ts`)

- `CallContext` gained `files` (the `$_FILES` equivalent: `{name,
  type, bytes}` per field, multipart only) and required
  `requestUri`. `Handler` may now return a full `Response` in
  addition to a JSON value.
- The handler is resolved **before** the body is read, so multipart
  requests can use `formData()` (`req.text()` would consume the
  stream first). Multipart text fields → `params`/`rawParams`, files
  → `ctx.files` (Buffer via `arrayBuffer()`); CSRF uses the
  form-field `CSRFToken` for multipart too.
- A `Response` result is returned verbatim with `setCookies`
  appended, never envelope-wrapped. `FB_PARITY` comparison is
  skipped for multipart requests and `Response` results. The proxy
  path is unchanged (binary passthrough, `content-disposition`
  forwarded). The dispatch rule stands: a registered handler's
  throw becomes the error envelope, NOT a proxy.

### CSV exports (`csv.ts`, new)

`exportCsvResponse` implements the League Csv Writer +
`EscapeFormula` rules verified live with sandbox PHP: `'` prepended
when a string cell starts with `= - + @ \t \r`; quoting (inner `"`
doubled) when the value contains `,` `"` `\` `\n` `\r` `\t` or
space; `;` `:` `'` VT FF never quoted; backslashes inside quoted
fields pass through undoubled; NULL renders empty. Service rule:
requested headers intersected with `EXPORTABLE_COLUMNS` in
EXPORTABLE order (parity24 includes a reversed-order case,
`[email, id]` → output `[id, email]`); empty intersect → DEFAULT
columns. Factory rule: sensitive columns (`pass`, `salt`,
`api_token`, `hash`, `config`) stripped; no headers → derive from
first-row keys minus sensitive; headers-but-zero-rows → header row
only; no-headers-and-zero-rows → empty body. Headers exactly as
PHP: `text/csv; charset=utf-8`, `attachment; filename=<name>.csv`,
`Cache-Control: no-cache, must-revalidate`,
`Expires: Mon, 26 Jul 1997 05:00:00 GMT` (PHP's session-added
`private` token in Cache-Control is a transport artifact; parity24
normalizes it out, order-insensitively). CSV bodies compared
byte-exact across stacks (12 cases × 3 modules).

### Guest invoice `payment` (`invoice.ts`, `payment-adapters.ts`, `stripe-forms.ts`)

Exact check order from `Guest.php` + `processInvoice`: hash empty →
810, bad hash format → 4001, gateway_id empty (`"0"` counts as
empty under PHP `empty()`) → 811, invoice lookup → 812,
`checkInvoiceAuth` 403s, canceled/replaced → 403, already paid →
403, gateway lookup (`(int)` cast) → 813, disabled → 814,
not-subscribable + single-not-allowed → 815. The request's
`subscribe` param is IGNORED by PHP; only `allow_subscription`
matters. `subscribe` itself = `isSubscribable` (pure
`invoice_item` query: all priced lines share one non-empty period)
AND gateway `allow_recurrent` AND `allow_subscription`.
`invoiceArray`'s subscription was NOT reused: it is type-filtered
(`type === "order"`), while the payment path uses the pure query
with no type filter — a new `subscriptionPeriodForInvoice` helper
implements the pure query (the display divergence is pre-existing
and out of scope).

All three in-tree adapters with gateway rows implement `getHtml`,
so `processInvoice` always returns `{iframe, type: 'html',
service_url: '', subscription, result: html}`:

- **Custom**: config `single`/`recurrent` template via sandboxed
  Twig (`renderTemplateStrict`) + a conservative sanitizer
  approximation (safe elements kept, event attributes and unsafe
  schemes dropped, text-node `"` → `&#34;`). The reference NULL-config
  fallback renders byte-exact:
  `&#34;Custom&#34; payment adapter is not fully configured.`
  Configured-template fidelity is a documented gap (see §7).
- **PayPalEmail**: exact field orders, charset cases (lowercase
  one-time, uppercase subscription), `item_name` =
  `Payment for invoice:serie:id [:title]` with `%05d` nr,
  `moneyFormat` (Intl fraction digits + half-away-from-zero),
  `htmlspecialchars` ENT_QUOTES mapping, signed notify URLs
  (HMAC-SHA256 `"<gatewayId>|<invoiceId>"`, `FB_CALLBACK_SALT`).
  Byte-exact on the same install (deterministic signatures).
- **Stripe**: one-time and subscription templates extracted
  byte-for-byte from `Stripe.php` by an ephemeral script
  (`stripe-forms.ts` header says how to regenerate); direct Stripe
  REST calls with identical params and idempotency keys
  (`one_time_invoice_{id}_gateway_{gid}_{sha256(json)}`,
  `setup_intent_invoice_{id}_gateway_{gid}_{sha256(json)}` schemes);
  customer/price caches (`pay_gateway_customer`,
  `pay_gateway_product`) with unique-violation re-read; subscription
  lock as an in-process promise-chain mutex (an earlier draft could
  deadlock and was replaced — do not reintroduce it); key checks
  before any API call (missing key → 4001 message); SDK/transport
  failures → the generic envelope (`An unexpected error occurred.
  Please try again later.`, 9999), matching PHP's dispatcher mapping
  of non-FOSSBilling exceptions. **Live Stripe success is
  unverified** (sandbox TLS fails; both stacks return the generic
  envelope in parity24 — see §7).
- Any other gateway code throws
  `Payment adapter <code> is not supported by the TypeScript port.`
  — never proxied, never fabricated. ClientBalance has no `getHtml`
  path and is out of scope.

### Guest invoice `pdf` (`invoice.ts`, `pdf.ts`)

Param checks (missing hash → `Invoice hash was not passed`, 9999;
bad format → 4001), then `checkInvoiceAuth` READ, then
`invoicePdfByHash`. Disposition follows PHP's serie_nr rule
(`inline; filename=FOSS09001.pdf`, unquoted for token-safe names;
`filename*` fallback otherwise) — note the existing client pdf
route's `invoice-<hash>.pdf` naming diverges from PHP and was NOT
copied here. Parity compares status, content-type, disposition
filename, `%PDF-` magic, and non-empty body — never PHP bytes
(dompdf output is non-deterministic across runs; `pdf.ts` is a
clean-room same-data layout, not a pixel clone).

### Servicedownloadable binary endpoints (`servicedownloadable.ts`)

- **Admin `upload`**: Api-level no-file check FIRST
  (`File was not uploaded.`, distinct from the service-level
  message). Extension allowlist checked first (lowercased
  `pathinfo` semantics: no dot or leading-dot-only → `''`;
  disallowed → `File extension:ext is not allowed. Allowed
  extensions: <comma-space list>`), then filename (string,
  non-empty, ≤255), label (trim, empty→null, ≤255), description
  (≤1000). Stored name = fresh 64-hex looped while the file
  exists; definition id = 32 hex. Appends to product config
  `files[]`; cascades to orders when `update_orders` is set
  (order configs + service files at sort_order = current count).
  MIME mismatch only logs a warning in PHP and still accepts —
  TS is extension-only (documented; TS cannot do server-side MIME
  detection the way PHP does).
- **Admin `update`**: service-level no-file message
  (`File upload failed: no files in request.`), no status check
  (matching PHP), inserts a service file + appends to order config.
- **Admin `send_file`**: hex `file_key` (bad format or unknown →
  `File not found`), NO download counting.
- **Admin `send_order_file`**: numeric service-file id, NO counting
  (capture-confirmed: downloads stayed 0).
- **Client `send_file`**: `Order ID is required` (also for `"0"`,
  PHP `empty()`), `File ID is required` (but `"0"` passes to the
  lookup), owned-order lookup else `Order not found`, `expires_at`
  ≤ now → `Subscription expired`, service null or status ≠
  `active` → `Order is not activated`, counting (capture-confirmed:
  downloads became 1). Missing disk file → 404
  `File cannot be downloaded at the moment. Please contact support.`
  on all three send paths. Send headers: `application/octet-stream`,
  disposition, `Cache-Control: public`, `Last-Modified` = file
  mtime, `Content-Length`, `Accept-Ranges: none` (parity24
  compares bytes + all but Last-Modified, which differs when
  fixtures are re-created per stack).

## 7. Divergences and unverified-live items (complete list)

1. **Stripe payment success path** — implemented via direct REST
   with identical params/idempotency/caches, but live success is
   unverified (sandbox TLS fails; both stacks return the generic
   9999 envelope in parity24). Real field casing/date formats on
   live Stripe responses are the residual risk. Same caveat class
   as the eNom adapter's pending live verification.
2. **`update_rates` live happy path** — verified for TS (§1), not
   for PHP (sandbox TLS). No action needed; the asymmetry is
   documented, not hidden.
3. **Custom gateway configured-template fidelity** — the
   NULL-config fallback path matches byte-exact; a configured
   Twig template goes through `renderTemplateStrict` + the
   sanitizer approximation, whose fidelity against PHP's sandboxed
   Twig + Symfony HtmlSanitizer is unverified (no configured Custom
   template exists on the reference install).
4. **TS Twig `{% set %}`** — still not evaluated on sends
   (pre-existing gap, plan R5).
5. **Guest pdf bytes** — clean-room layout, not a dompdf clone
   (status/headers/magic/content compared, never bytes).
6. **Downloadable MIME check** — TS is extension-only; PHP logs a
   warning on MIME mismatch and still accepts (same outcome).
7. **HTTP status on TS error envelopes** — always 200 (seam-wide
   convention); PHP uses 404 for the missing-disk send_file case
   and other non-200 statuses elsewhere. Envelopes are identical;
   only the status differs (§6).
8. **String `headers` param on `export_csv`** — PHP would TypeError
   (9998) on a non-array value; TS accepts JSON-array or bracket
   form params only. Parity does not cover the string case.
9. **PHP `run_check`/`run_checks` and servicecustom `__call`/`call`**
   remain proxied by design (deferred, §2–§3); `run_checks` was
   not exercised in parity24 (see §5).
10. **`update_cache_settings` flat-vs-nested param** — documented
    in §2; TS deletion makes the question moot going forward.
